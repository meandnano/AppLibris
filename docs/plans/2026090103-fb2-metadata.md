# Step: FB2 metadata and cover extraction

## Context

Promoted from `docs/backlog/2026083119-fb2-metadata.md`, deleted in this
change. That file's own re-validation note said to reassess once EPUB
metadata completeness landed, because it would widen the gap. It has
(`2026083114`, merged as #16), and it did.

`scanner.extractMetadata` still opens with:

```go
if ext != ".epub" {
    return bookMeta{Title: fallbackTitle}
}
```

So every FB2 book in the library is a card with the filename as its title,
"Author unknown", and a "no cover" placeholder. Meanwhile every EPUB now
carries title, authors, language, description, cover, **and** publisher,
publication date and an ISBN recognised in three forms. `bookMeta` has
eight fields; an FB2 book populates one of them.

For FB2 that filename is often the worst possible title — the format is
overwhelmingly distributed by aggregator sites that name files by
transliteration or numeric id, so the grid shows rows of
`ivanov_i_nazvanie_123456` where the EPUBs beside them show real titles.

**Two things verified on current master while validating**, both of which
shape the work:

**1. A `.fb2.zip` file would be invisible to the scanner entirely.** The
walk filters on `filepath.Ext`, and `filepath.Ext("book.fb2.zip")` is
`".zip"`, which is not in `supportedExtensions`. Such a file would not be
mis-parsed — it would never be seen at all, and nothing would report it
skipped.

The collection contains none today, so this is not currently costing
anything; FB2 is nonetheless commonly distributed zipped, one book per
archive, so it is a plausible future import. It stays in scope on cost
grounds rather than urgency — see the `.fb2.zip` section for the sizing.

**2. A `windows-1251` FB2 fails to parse outright, not partially.**
`encoding/xml` returns

```
xml: encoding "windows-1251" declared but Decoder.CharsetReader is nil
```

and decodes nothing. This is not the mojibake the backlog file guessed at —
it is a hard error, so without a `CharsetReader` a cp1251 book would fall
straight back to the filename title and look exactly as broken as it does
today. Since cp1251 is the dominant encoding for Russian-language FB2, and
Russian is the dominant language for the format, this is the difference
between the step working and not working.

## Scope

In scope: a new `internal/fb2` package, wiring it into
`scanner.extractMetadata`, and recognising `.fb2.zip`. Out of scope:
conversion (DESIGN.md defers it, and nothing here depends on it), and any
change to `internal/cover` — verified it still takes raw bytes and infers
the format via `image.Decode`, with JPEG, PNG and GIF registered, which
covers what FB2 `<binary>` elements carry.

No schema change and no migration: every column this populates already
exists and is already written for EPUBs.

## The dependency question

Decoding cp1251 needs a `CharsetReader`. Two options, and the project's
stated bar is "pull in a library only when it saves real logic" — the
reasoning that kept `resend-go` out for one JSON POST.

**Recommended: `golang.org/x/text/encoding/charmap` + `ianaindex`.** It
clears that bar. Character tables are not logic you want to hand-write:
getting one entry wrong produces a book title that is subtly wrong rather
than obviously broken, in a language the maintainer may not read, and it
covers cp1252, koi8-r and the iso-8859 family for free. It is also the same
`golang.org/x/*` family as the already-accepted `x/image`. Note it is a
genuinely new module — it is not currently in the module cache — so the
first build after this needs network.

**Alternative, if the collection turns out to be cp1251-only:** a hand-rolled
256-entry table is about forty lines and no dependency. Legitimate, and
worth taking if the encoding survey above comes back uniform. Do not take it
on a mixed collection — the failure mode is silent.

Either way the `CharsetReader` should **fall back to passing the input
through unchanged for an unknown encoding label** rather than erroring.
A mislabelled-but-actually-UTF-8 file is common, and a filename title is a
worse outcome than a best-effort parse.

## `internal/fb2` (new package)

Mirror `internal/epub`'s surface exactly, so the scanner stays ignorant of
format detail:

```go
type Metadata struct {
    Title         string
    Authors       []string
    Language      string
    ISBN          string
    Description   string
    Publisher     string
    PublishedDate string
    Cover         []byte
}

func ReadMetadata(path string) (Metadata, error)
```

Same field set as `epub.Metadata`, deliberately — `bookMeta` already has
these eight fields and the scanner should be able to fill them from either
source with the same code shape.

**Structure to parse.** FB2 is one XML document; everything needed is under
`<description>`, plus `<binary>` elements at the document root:

| `Metadata` field | FB2 source |
|---|---|
| `Title` | `description/title-info/book-title` |
| `Authors` | `description/title-info/author` (structured — see below) |
| `Language` | `description/title-info/lang` |
| `Description` | `description/title-info/annotation` |
| `Publisher` | `description/publish-info/publisher` |
| `PublishedDate` | `description/publish-info/year`, falling back to `title-info/date` |
| `ISBN` | `description/publish-info/isbn` |
| `Cover` | `<binary>` whose `id` matches `title-info/coverpage/image/@l:href` |

**Authors are structured, not a display string.** FB2 gives
`<first-name>`, `<middle-name>`, `<last-name>` as separate elements, where
`dc:creator` gives one string. The `authors` table stores one name, so join
non-empty parts with a single space in first-middle-last order. Record that
choice in a comment: it is the one place FB2 offers more structure than the
schema keeps, and a future browse-by-author might want it back.

**`PublishedDate` prefers `publish-info/year`.** Per the FB2 spec
`title-info/date` is when the work was *written*; `publish-info/year` is
when this edition was *published*, which is what `books.published_date`
means. Fall back to `title-info/date`'s `value` attribute, then its text.
Store the value as found without normalising — same rule
`2026083114-epub-metadata-completeness` established for `dc:date`, for the
same reason.

**`annotation` contains markup.** It holds `<p>` elements, sometimes with
nested emphasis. Decode it as `P []string \`xml:"p"\`` and join with a blank
line. That drops inline markup, which is correct here: `epub`'s
`Description` is plain text and the template renders it as such, so the two
formats should produce the same kind of value.

**The cover reference is namespaced.** `<image l:href="#cover.jpg"/>` uses
xlink. Tag it `xml:"href,attr"` — Go matches on local name when no namespace
is given, the same trick `epub`'s `scheme,attr` already relies on. Strip the
leading `#`, then find the `<binary>` with that `id` and base64-decode its
chardata. Return nil on any mismatch rather than erroring, matching
`epub.readCover`: a missing cover must never invalidate the rest of the
metadata.

**Charset.** Set `decoder.CharsetReader` per the dependency section. This is
the one line that decides whether cp1251 books work at all.

## `.fb2.zip`

**There are no `.fb2.zip` files in the collection today.** This is built
forward-looking, on the grounds that it is cheaper now than later:

| | |
|---|---|
| Lines of new logic | ~20, and `internal/epub`'s `ReadMetadata` is the pattern to copy verbatim — open the zip, find the entry, parse it |
| Existing lines touched | 5, all in `scanner.go` (see below) |
| Of those, already being rewritten by this step anyway | 3 |
| Regression risk | confined to one line — the walk filter, the only extension check shared with EPUB |

Deferring it would mean re-opening `internal/fb2` *and* redoing the
extension refactor as a separate change later, for the same total work
split across two steps. And unlike the charset work, zip handling is
deterministic: synthetic fixtures verify it completely, so having no real
`.fb2.zip` files costs no confidence here.

If it is dropped anyway, drop only this section — nothing else in the plan
depends on it.

Recognising these means the extension check can no longer be
`filepath.Ext`. Keep it simple and explicit — lowercase the name once and
test suffixes:

```go
var supportedSuffixes = []string{".epub", ".fb2", ".fb2.zip"}
```

`fb2.ReadMetadata` then branches on the suffix: a plain `.fb2` is parsed
directly; a `.fb2.zip` is opened with `archive/zip` and the single `.fb2`
entry inside it is parsed. If an archive holds no `.fb2` entry, or more than
one, return an error and let the scanner fall back to a filename title —
do not guess which book an ambiguous archive contains.

**The five places `ext` is currently assumed to be one `filepath.Ext`
segment**, so none is missed: the walk filter (`scanner.go:103`), the
`ext :=` derivation and its use in `extractMetadata` and `Format`
(`381`, `430`, `407`), and `filenameTitle` (`459`).

That last one is a real gap, not bookkeeping. `filenameTitle` strips
`filepath.Ext(base)`, which takes only `.zip` — so `book.fb2.zip` falls
back to the title **`book.fb2`**, extension and all, on any file whose
metadata fails to parse. Strip the whole matched suffix instead, or the
fallback title is visibly wrong in the grid for exactly the files most
likely to need a fallback.

Content hashing is unaffected and needs no thought: identity is the hash of
the file on disk, and for a `.fb2.zip` that is the archive. The same book
stored both zipped and unzipped is two different hashes and therefore two
books, which is correct under DESIGN.md's byte-identical-only v1 rule —
near-duplicate detection is what would eventually merge them, and it is
deferred.

`books.format` should record `fb2` for both, not `fb2.zip`. The format badge
tells the reader what the book *is*; how it is stored on disk is not
something the UI should surface. `strings.TrimPrefix(ext, ".")` no longer
produces the right value, so derive it from the matched suffix.

## `internal/scanner` changes

`extractMetadata` becomes a switch on the matched suffix with two arms and
no other change in shape:

```go
switch {
case suffix == ".epub":
    m, err := epub.ReadMetadata(path)
    // ...
case suffix == ".fb2", suffix == ".fb2.zip":
    m, err := fb2.ReadMetadata(path)
    // ...
}
```

Both arms do the same thing with their result — fall back to the filename
title when the parse fails or yields no title, log the failure at Warn, and
copy the eight fields across. The two `Metadata` types are structurally
identical but deliberately distinct types (no shared interface): there are
exactly two implementations, neither is chosen at runtime, and an interface
here would buy nothing that a switch does not. Extract the field-copying
into a small helper if the two arms end up duplicating it verbatim.

Existing FB2 books in an index **will not** pick this up on their own —
metadata is parsed only on first sight of a content hash. Same limitation
`2026083114` documented, same eventual fix (a re-parse pass, which is the
enrichment queue's machinery). The interim answer for a personal library is
to delete the database and rescan; say so in the commit message.

## Tests

`internal/fb2`, with fixtures built in-test the way `epub_test.go` builds
EPUBs:

- A full document: title, a multi-part author name joined correctly,
  language, annotation, publisher, year, ISBN, and a cover.
- **A `windows-1251` document parses and returns correctly-decoded
  non-ASCII text.** This is the test the whole encoding decision exists for,
  and it fails with a bare `xml.Decoder` — confirmed on master, where the
  decoder returns `encoding "windows-1251" declared but Decoder.CharsetReader
  is nil` and reads nothing.
- An unknown encoding label falls back to a best-effort parse rather than
  erroring.
- Author name assembly: first+last only (no middle), last only, and all
  three.
- `publish-info/year` wins over `title-info/date`; `title-info/date` is used
  when `publish-info` is absent.
- A `coverpage` pointing at a `binary` id that does not exist returns nil
  cover and intact metadata — the FB2 mirror of
  `TestReadMetadataCoverDanglingReference`.
- A `.fb2.zip` containing one `.fb2` parses; one containing zero or two
  returns an error. These fixtures are the *entire* verification surface
  for zip support, since the collection has no such files to try it
  against — which is fine here, as zip structure is deterministic in a way
  character encodings are not.
- `filenameTitle` on `book.fb2.zip` yields `book`, not `book.fb2`.
- A file that is not XML at all returns an error rather than panicking.

`internal/scanner`:

- Scanning a `.fb2` produces a book with real title, author and cover — not
  the filename. This is the end-to-end regression for the whole step.
- Scanning a `.fb2.zip` indexes it at all, with `format` recorded as `fb2`.
  On master it is not indexed, so assert the book count, not just its
  fields.
- An unparseable `.fb2` still yields a book with the filename title and
  counts no error — degrading, not failing, matches how a bad EPUB behaves.
