# Step: Resend mail integration

## Context

DESIGN.md's Send to Kindle section names three things send-to-Kindle needs
before it can be built: an FTS5 index (for search, not this step), a
`recipients`/`send_log` schema, and **the mail integration** — a way to
actually hand an attachment to Resend, DESIGN.md's chosen transport
("already in use"). This step is that third piece, on its own: a small
package that can send one email with one attachment through Resend's API
and enforce the size limit DESIGN.md derives, with nothing above it yet.

**Why Resend and not raw SMTP.** Considered and decided against for now:
raw SMTP means owning MIME/attachment construction and auth, and — more
importantly — an SMTP `250 OK` only means "a server accepted it," not
"Amazon delivered it," which is weaker than the delivered/failed signal the
job model in DESIGN.md wants. Resend's API gives that signal (a message id
now, delivery/bounce webhooks later) for one HTTP call. This is a
transport choice, not a locked door — if it's ever revisited, nothing here
needs to change shape to add an alternative, because there is deliberately
no `Sender` interface yet (see Scope).

**Scope boundary.** This step is the transport primitive only:
`internal/resend`'s `Client.Send`. Out of scope, because DESIGN.md
describes them as separate prerequisites and each gets its own plan: the
`recipients`/`send_log` schema, the queued/sending/delivered/failed job
model and its retry button, the service method and web handler that would
call `Send`, and the recipient-picker UI. No `Sender` interface or provider
abstraction either — DESIGN.md's provider-chain pattern earns its interface
because multiple metadata providers really are chained at once; mail has
exactly one active transport, so an interface now would be speculative
generality with nothing yet to justify it (and the user has explicitly
deferred revisiting SMTP as an alternative, not asked for both at once).

## `internal/resend` (new package)

A small wrapper over Resend's `POST /emails` endpoint via `net/http` and
`encoding/json` — one endpoint, one call shape, not enough surface to
justify a new dependency on the `resend-go` SDK.

**`resend.go`**
- `Attachment` struct: `Filename string`, `Content []byte`.
- `Client` struct: `apiKey`, `from string`, `baseURL string` (defaults to
  `https://api.resend.com`, unexported and overridden directly by
  same-package tests against an `httptest.Server` — no `Option`/functional-
  argument plumbing for a single test-only knob), `httpClient *http.Client`.
- `NewClient(apiKey, from string) *Client`.
- `func (c *Client) Send(ctx context.Context, to string, a Attachment) (id string, err error)`:
  1. Size check first (see below) — fail before making any HTTP call.
  2. Build Resend's JSON body: `from`, `to: [to]`, a static `subject`
     (e.g. `"Sent from Bookshelf"`) and empty/minimal `text` body — Amazon's
     send-to-Kindle only looks at the attachment, so the message text is
     not user-facing content worth making configurable here — and
     `attachments: [{filename, content: base64(a.Content)}]`.
  3. POST with `Authorization: Bearer <apiKey>`, `Content-Type:
     application/json`, `ctx` on the request.
  4. Non-2xx response → read and wrap Resend's JSON error body (`message`,
     `name`) into the returned error rather than a bare status code, so a
     caller logging the error has something actionable.
  5. On success, return Resend's `id` from the response body — the future
     `send_log` step will want it to correlate delivery/bounce webhooks
     against a send row, and discarding it now would mean re-deriving it
     later.
- No retry loop and no logging inside this package: DESIGN.md's retry is a
  user-initiated button (re-enqueue, call `Send` again), not automatic
  backoff, and every other leaf package in this codebase (`internal/epub`,
  `internal/cover`) returns errors rather than logging them — the caller
  decides the level, same as scanner already does for `epub`/`cover`
  errors.

**Size limit**
- `const MaxAttachmentSize = 28 * 1024 * 1024` with the arithmetic from
  DESIGN.md in a comment: Resend caps the whole message (headers + JSON +
  base64 attachment) at 40MB; base64 inflates raw bytes by ~4/3, so 40MB of
  message allows roughly 30MB of raw attachment; enforce 28MB to leave
  headroom for headers and the rest of the JSON body. (Amazon's own 200MB
  cap is well above this and isn't the binding constraint, per DESIGN.md.)
- `Send` checks `len(a.Content)` against it before building the request and
  returns a sentinel-wrapped error (`ErrAttachmentTooLarge`, checkable with
  `errors.Is`) carrying the actual size — callers need to distinguish "too
  large, tell the user clearly" from "Resend/network failure, maybe retry,"
  and DESIGN.md is explicit this check happens client-side before the send
  is attempted, not as a Resend API error to parse.

**`resend_test.go`**
- An `httptest.Server` stands in for Resend: asserts method, path, the
  `Authorization` header, and the decoded JSON body (recipient, base64
  attachment content matches the input bytes); returns a canned success
  body (`{"id": "..."}`) or a canned error body per test case.
- Cases: successful send returns the id from the mocked response; a
  non-2xx response returns an error wrapping Resend's message; an
  oversized attachment returns `ErrAttachmentTooLarge` **without any
  request reaching the test server** (assert the server saw zero hits) and
  without needing a real API key.

## Dependency

None new — `net/http`, `encoding/json`, `encoding/base64` are all stdlib.
Matches the project's existing bar for pulling in a library only when it
saves real logic (`golang.org/x/image`'s scaling, `modernc.org/sqlite`'s
whole engine), which one JSON POST doesn't clear.

## CLAUDE.md

Add `internal/resend` to "Current implementation": a `Client.Send` that
POSTs an attachment to Resend's API, enforcing DESIGN.md's ~28MB size
limit before attempting a send; no recipients/send_log/job-queue wiring
yet — nothing calls it. Leave send-to-Kindle itself on the "still missing"
line; this step doesn't remove it, only removes one of its three
prerequisites.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` clean, including the
  new `internal/resend` tests above.
- No manual end-to-end step against the real Resend API: nothing in the
  binary calls `Send` yet (`cmd/server` is untouched — no `RESEND_API_KEY`/
  `RESEND_FROM` env vars are wired in until the step that actually
  constructs a `Client` and uses it exists), so the `httptest`-backed unit
  tests are the whole verification surface here.
