# Step: Structured logging with slog

## Context

Every log line today goes through the standard `log` package, called
directly from `cmd/server/main.go`, `internal/scanner`, and `internal/web`:
`log.Printf` for anything that isn't fatal, `log.Fatalf` for startup
failures. There are no levels — a per-file scan warning and a request
failure print identically — and per-item context (a file path, an error) is
baked into the message string via `Printf` rather than carried as separate
fields, so it's not filterable or machine-parseable. As the app's moving
parts grow (periodic scans, HTTP requests, startup migrations), there's no
way to turn the noise down in normal operation or up when diagnosing
something, and no single place currently says "the app is alive and doing
X."

This step replaces `log` with the standard library's `log/slog` (available
since Go 1.21; this module is already on `go 1.26.1`, so no new dependency),
assigns every existing call site a real level, converts interpolated
details into structured attributes, and adds a `LOG_LEVEL` env var so the
threshold is configurable without a rebuild. Output stays plain text via
`slog.NewTextHandler` — this project has no log aggregation pipeline to want
JSON for, and text keeps `go run ./cmd/server` output as readable as it is
today.

## Scope

In scope: swapping every `log.Printf`/`log.Fatalf` call for the
appropriately-leveled `slog` equivalent with structured attributes, the
`LOG_LEVEL` env var and the process-wide default logger it configures, and
a couple of new Debug/Info lines at points that are currently invisible
end-to-end (a scan starting, a migration applying) — not new instrumentation
beyond what's needed to make the lifecycle events that already exist
observable.

Out of scope: HTTP access-log middleware (no request logging exists today;
adding one is a separate, bigger decision than re-leveling what's already
there), log output other than stderr (no rotation/file sink — matches
today), JSON output (no consumer for it yet).

## `LOG_LEVEL` and the default logger

- New env var, `LOG_LEVEL`, read in `cmd/server/main.go` alongside the
  existing `envOrDefault`-driven vars (`DB_PATH`, `ADDR`, `LIBRARY_DIR`,
  `COVERS_DIR`, `SCAN_INTERVAL`). Default `"INFO"`.
- Parsed with `(*slog.Level).UnmarshalText` rather than a hand-rolled
  switch — it already accepts `"DEBUG"/"INFO"/"WARN"/"ERROR"`
  case-insensitively, one less thing to keep in sync with slog's own level
  names. An unparseable value is a startup config error, handled the same
  way the existing `SCAN_INTERVAL` parse failure is: logged and the process
  exits.
- `main.go` builds the process-wide logger first, before anything else can
  log: `slog.SetDefault(slog.New(slog.NewTextHandler(os.Stderr,
  &slog.HandlerOptions{Level: level})))`. Every other package keeps calling
  the package-level `slog.Info`/`Warn`/`Error`/`Debug` functions (which use
  the default logger) rather than taking an injected `*slog.Logger` —
  mirrors how they already call the global `log` package today, and nothing
  here needs per-component configuration (request-scoped fields, separate
  sinks per package) that would justify threading a logger through
  constructors.
- `slog` has no `Fatal` helper, so every current `log.Fatalf` call site
  becomes two lines — `slog.Error(msg, "error", err)` then `os.Exit(1)` —
  written out directly at each of the five sites rather than behind a
  `fatal(...)` helper; they're already five separate, differently-worded
  calls today, so this isn't new duplication, just the same shape restated
  in two lines instead of one.

## Message style

Static lowercase message, dynamic detail as attributes — not interpolated
into the message string — so a log line's variable parts are filterable
key/value pairs under the text handler, not free text to regex:
`slog.Warn("scan file failed", "path", path, "error", err)`, not
`slog.Warn(fmt.Sprintf("scanner: %s: %v", path, err))`.

## Level assignments

**`cmd/server/main.go`**
- Startup failures (bad `SCAN_INTERVAL`, can't create `LIBRARY_DIR` or
  `COVERS_DIR`, can't open the DB, `ListenAndServe` returning) → Error +
  `os.Exit(1)`, same failures that are `log.Fatalf` today.
- `"listening"` (`addr`, `db_path` attrs) → Info — the one "server is up"
  line.
- A scan run's outcome → Info when `result.Errors == 0`, **Warn** when
  `result.Errors > 0` (attrs `scanned`, `new`, `moved`, `unchanged`,
  `errors`) — today "3 errors" and "0 errors" log identically at the same
  unleveled call; a sweep that completed but dropped files should stand
  out. The sweep failing outright (e.g. the library root doesn't exist)
  stays Error.
- New: Debug `"scan starting"` (attr `library_dir`) at the top of each run —
  cheap confirmation, at `LOG_LEVEL=debug`, that the periodic timer is
  actually firing, otherwise invisible between two "scan complete" lines an
  interval apart.

**`internal/scanner/scanner.go`**
- Per-file scan failure (`scanFile` erroring) → Warn (`path`, `error`) — the
  sweep continues past it.
- Cover storage failure → Warn (`path`, `error`) — the book row is still
  created, without a cover.
- Embedded metadata read failure → Warn (`path`, `error`) — falls back to a
  filename title.
- Nothing in this package rises to Error: every failure here is already
  handled by skipping or falling back, which is what makes it Warn
  throughout rather than Error.

**`internal/web/web.go`**
- `ListBooks` failure while serving `GET /` → Error (`error`) — the request
  fails with a 500.
- Template render failure → Error (`template`, `error`).

**`internal/storage/migrations.go`**
- New: Debug per applied migration (attr `version`, the migration's
  filename) — nothing observes migrations running today, so a slow or hung
  startup gives no way to tell "still migrating" from "stuck opening the
  DB" without this.

## CLAUDE.md

Add `LOG_LEVEL` to `cmd/server`'s env var list, and note that logging goes
through `log/slog` (text handler, leveled via `LOG_LEVEL`) rather than the
plain `log` package.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` clean. None of the
  existing tests capture log output (they assert on HTTP status/body or DB
  state), so switching the logging call sites doesn't touch test behavior.
- Manual: `LOG_LEVEL=debug go run ./cmd/server` against a populated
  `LIBRARY_DIR` and confirm the new "scan starting" and per-migration lines
  appear, with `path`/`version`/etc. as separate `key=value` pairs in the
  text output; rerun with the default level and confirm those two lines are
  gone but "scan complete" and "listening" still appear; drop a corrupt
  EPUB or an unreadable file into `LIBRARY_DIR` and confirm the resulting
  scan logs at Warn with structured `path`/`error` attrs, and that a run
  with such a failure logs "scan complete" at Warn (not Info) with
  `errors` > 0.
