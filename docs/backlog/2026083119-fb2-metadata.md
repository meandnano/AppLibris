# Backlog: FB2 metadata and cover extraction

## Problem

FB2 files are indexed but understood only as far as their filename.
`scanner.extractMetadata` short-circuits on anything that isn't `.epub`:

```go
if ext != ".epub" {
    return bookMeta{Title: fallbackTitle}
}
```

So an FB2 book gets a `books` row whose title is the filename with the
extension stripped, no authors, no language, no ISBN, no description, and no
cover. In the library grid it renders as an "Author unknown" card with a
"no cover" placeholder and whatever the downloader happened to name the
file — which for FB2 is frequently a transliterated or ID-shaped name.

DESIGN.md describes the collection as "EPUB (some FB2)", so this affects a
minority of the library, but a visibly degraded minority.

## Why this is backlog, not a plan

"Some FB2" — the format is a minority of the collection, the books are
still findable and sendable (Amazon does not accept FB2 directly, but that
is a conversion question, not a metadata one), and every EPUB-focused
improvement benefits more books per unit of work.

More importantly, this is **not a small addition to `internal/epub`**. It is
a second parser with a different shape, and pretending otherwise is how it
gets underestimated:

- FB2 is a single XML document, not a zip container. There is no OPF, no
  manifest, no `container.xml` — the metadata lives in
  `<description><title-info>`, with authors as structured
  `<first-name>`/`<middle-name>`/`<last-name>` elements rather than the
  single display string `dc:creator` gives.
- The cover is **base64-encoded inside the XML**, as a `<binary>` element
  referenced by `<coverpage><image l:href="#cover.jpg"/>`. So cover
  extraction is "find the binary element whose id matches, decode it",
  not "open a file in a zip" — a completely different code path from
  `epub.readCover`, though it produces the same `[]byte` for
  `cover.Store`.
- FB2 files are commonly distributed as `.fb2.zip`, which the scanner's
  extension check does not currently recognise at all.
- Encoding matters. FB2 predates the assumption of UTF-8 and files
  routinely declare `windows-1251` in the XML prolog. Go's
  `encoding/xml` will not decode those without a `CharsetReader`, so a
  Russian-language FB2 either fails to parse or produces mojibake — and
  Russian is the dominant language for the format. This needs
  `golang.org/x/text/encoding/charmap`, a new dependency, which is exactly
  the sort of decision worth making deliberately rather than mid-step.

That is a genuine step's worth of work, and it should be planned as one
when it comes up — not smuggled in as "also handle FB2".

## Sketch

A new `internal/fb2` package mirroring `internal/epub`'s surface — a
`Metadata` struct and a `ReadMetadata(path string) (Metadata, error)` — so
`scanner.extractMetadata` becomes a switch on extension with two arms and
no other change. Keeping the two parsers as sibling packages with the same
shape, rather than one package with a format flag, is what keeps the
scanner ignorant of format details.

Author names need joining from their parts into the single display string
the rest of the system expects (`first middle last`, with empties
collapsed), which is a small formatting decision worth writing down: the
`authors` table stores one name string, and FB2 is the only source that
offers structure.

## Validate before planning

- Check what the actual FB2 files in the collection look like before
  designing for the general case: how many are `.fb2` vs `.fb2.zip`, what
  encodings they declare, and whether they carry covers at all. A handful
  of real files will settle more design questions than the spec will.
- Confirm `internal/cover` still takes raw bytes and infers the format
  (it uses `image.Decode` with PNG/GIF/JPEG registered), so an FB2 cover
  needs no changes there.
- Decide whether conversion (FB2 → EPUB, for actually sending to a Kindle)
  is close enough on the roadmap that metadata and conversion should be
  planned together — DESIGN.md defers conversion, so probably not, but it
  is worth a moment's thought since both touch the same files.
